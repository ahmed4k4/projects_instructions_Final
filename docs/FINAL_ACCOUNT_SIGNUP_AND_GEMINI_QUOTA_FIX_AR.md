# إصلاح التسجيل ومشكلة Gemini Quota — Nexus PC Builder 1.0.2

## ما الذي كان يحدث؟

- `POST /api/auth/signup 504`: مسار التسجيل كان ينتظر RPC الخاص بتحديد المحاولات دون مهلة محددة، ثم ينفذ إنشاء المستخدم، وبعدها كان المتصفح ينفذ طلب تسجيل دخول منفصل. اجتماع هذه الطلبات قد يتجاوز مهلة Vercel.
- `POST /auth/v1/token?grant_type=password 400`: كان يظهر بعد التسجيل عندما يفشل طلب تسجيل الدخول المنفصل أو عندما لا يكون الحساب قد أُنشئ/فُعّل كما ينبغي. السجل وحده لا يثبت سبب 400 الأصلي، لذلك أصبح التسجيل يعيد سببًا واضحًا ولا يعتمد على طلب متصفح ثانٍ بعد الإنشاء.
- Gemini `429`: هذا رفض من Google بسبب نفاد حصة المشروع أو تجاوز RPM/TPM/RPD. لا يستطيع كود الموقع تجاوز حدود Google أو إنشاء حصة مجانية إضافية.

## التغييرات

1. أزيل استدعاء Supabase SDK RPC غير المحدود من مسار التسجيل، واستُبدل بطلب REST بمهلة 900ms.
2. أضيف حد محاولات محلي لكل IP كحماية فورية حتى لو تعطل RPC الموزع. هذا الحد محلي لكل instance وليس بديلًا كاملًا عن rate limiter موزع.
3. طلب إنشاء مستخدم Supabase Admin له مهلة 3.5 ثانية.
4. بعد إنشاء الحساب، ينفذ الخادم password grant بمهلة 3 ثوانٍ ويرجع `access_token` و`refresh_token` إلى العميل.
5. العميل يحفظ الجلسة باستخدام `supabase.auth.setSession` بدل إرسال طلب تسجيل دخول ثانٍ.
6. إذا انتهى طلب سابق بعد إنشاء المستخدم، فإن إعادة المحاولة بنفس اسم المستخدم وكلمة المرور تحاول المصادقة على الحساب الموجود بدل إنشاء حساب مكرر.
7. تم تحسين رسائل تسجيل الدخول الخاطئ إلى رسالة عربية واضحة.
8. مفتاح `SUPABASE_SERVICE_ROLE_KEY` يظل على الخادم فقط، ولا يُستخدم في كود المتصفح.

## متغيرات Vercel المطلوبة

تأكد من وجود المتغيرات التالية في Production وPreview/Development حسب بيئتك:

- `VITE_SUPABASE_URL` — رابط مشروع Supabase المستخدم في الواجهة.
- `VITE_SUPABASE_ANON_KEY` — مفتاح anon/public.
- `SUPABASE_URL` — نفس رابط المشروع (مستحسن كمتغير خادمي صريح).
- `SUPABASE_ANON_KEY` — نفس مفتاح anon (مستحسن كمتغير خادمي صريح؛ ويمكن للمسار استخدام `VITE_SUPABASE_ANON_KEY`).
- `SUPABASE_SERVICE_ROLE_KEY` — المفتاح السري للخادم فقط، دون `VITE_` مطلقًا.
- `AUTH_RATE_LIMIT_SALT` — اختياري، قيمة عشوائية طويلة للخادم.

لا تضع service role key في Git أو `.env` الخاص بالواجهة أو أي متغير يبدأ بـ `VITE_`.

## بعد التحديث

1. استبدل المشروع بهذه النسخة.
2. راجع متغيرات Vercel أعلاه، ثم أعد Deploy لأن تغييرات Environment Variables لا تطبق على Deployment قديم.
3. جرّب إنشاء حساب جديد.
4. إذا انتهت محاولة سابقة بمهلة، جرّب تسجيل الدخول بنفس البيانات قبل إعادة إنشاء اسم مستخدم آخر.
5. إذا ظهر خطأ، افتح Vercel → Logs → Function `api/auth/signup`. ابحث عن `[auth signup]`؛ لا تشارك مفاتيح API أو كلمات المرور.

## Gemini 429 — إجراء مطلوب خارج الكود

إذا ظهرت رسالة `You exceeded your current quota`, فهذا يعني أن Google رفضت الطلب. كل مفاتيح API التابعة لنفس Google Cloud Project تشترك في حدود المشروع؛ تدوير API keys في المشروع نفسه لا يرفع الحصة.

- راجع Usage وRate limits للمشروع المرتبط بـ `GEMINI_API_KEY` في Google AI Studio.
- حدّد هل الحد المنتهي RPM أو TPM أو RPD.
- إذا كان RPM/TPM: انتظر إعادة الضبط وخفّض عدد/حجم الطلبات المتزامنة.
- إذا كان RPD: انتظر إعادة الضبط اليومية أو فعّل الفوترة/اطلب Tier أعلى إذا كان متاحًا.
- تأكد أن `GEMINI_API_KEY` في Vercel يشير إلى المشروع الذي راجعته، ثم أعد Deploy عند تغييره.

لا يوجد تعديل برمجي آمن يمكنه تخطي حصة Google. الإصدار يوقف المحاولات البديلة بعد 429 حتى لا يهدر مزيدًا من الطلبات، ويعرض رسالة السبب بدل تكرار الاستدعاءات.
