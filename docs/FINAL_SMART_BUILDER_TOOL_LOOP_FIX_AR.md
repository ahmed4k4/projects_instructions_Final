# التقرير النهائي — إصلاح دورة Smart Builder

## ملخص المشكلة

كان Smart Builder يعرض:

`AI temporarily unavailable — showing a rule-based build (the assistant did not finalise a valid build).`

أي أن مسار النموذج لم يصل إلى استدعاء `finalize_build` صالح، فانتقل التطبيق بصورة صحيحة إلى البناء الاحتياطي.

## السبب البرمجي الذي عالجته

1. كانت استدعاءات `list_components` المتوازية تُحوّل إلى رسائل user منفصلة؛ بينما يجب إرسال ردود الدفعة المتوازية في رسالة user واحدة تحتوي على عدة `functionResponse` parts.
2. كان المحول يفضّل ربط رد الأداة بالاسم على معرّف الاستدعاء الأصلي. مع تكرار اسم `list_components` كان ذلك قد يربط الرد بمعرّف طلب آخر.
3. Smart Builder كان يمرر `onToken` إلى `generate`، فيحوّل استدعاءات الأدوات إلى مسار SSE streaming. تم إيقاف streaming لدورات الأدوات في Smart Builder تحديدًا حتى يعيد الطلب الكامل `functionCall` و`thoughtSignature` دون تجميع أجزاء متفرقة.
4. لم يكن هناك ضمان أخير لإجبار النموذج على استدعاء الأداة النهائية إذا رجع بنص عادي بعد استعراض المنتجات.

## ما تم تغييره

- تجميع استجابات الأدوات المتوازية في رسالة Gemini user واحدة.
- الحفاظ على IDs الأصلية لكل `functionCall` و`functionResponse`، وعدم توليد ID مصطنع عندما لا يرسله Gemini.
- فصل مسار Smart Builder عن streaming أثناء دورات الأدوات؛ ما زال Advisor يستخدم streaming للنص.
- زيادة سقف مخرجات كل جولة إلى 3072 token.
- إضافة محاولة استرداد تفرض `list_components` إذا لم يبدأ النموذج باستدعاء الأدوات.
- إضافة محاولة نهائية تفرض `finalize_build` فقط عبر `toolConfig.functionCallingConfig.mode = ANY` و`allowedFunctionNames`.
- الإبقاء على التحقق الحتمي من IDs والتوافق والميزانية قبل إرجاع نتيجة AI.
- تحديث التوثيق وإضافة أمر تحقق مستقل `pnpm verify:build-loop`.

## فحص إضافي مطلوب على بيئة المشروع

لم يتوفر `node_modules` في بيئة الفحص، كما فشل Corepack في الوصول إلى `registry.npmjs.org` بسبب خطأ DNS (`EAI_AGAIN`). لذلك لم يكن ممكنًا تشغيل `pnpm typecheck` أو `pnpm test` أو `pnpm build` بالكامل هنا، ولم أجرِ طلبًا حيًا إلى Gemini بمفتاح المشروع.

بعد فك الضغط شغّل في جهازك:

```bash
pnpm install
pnpm verify:build-loop
pnpm verify:ai-speed
pnpm verify:guest-auth
pnpm verify:ai-route
pnpm typecheck
pnpm test
pnpm build
```

اختبار `verify:build` هو اختبار حي اختياري يحتاج `GEMINI_API_KEY` داخل `.env.local` أو متغيرات البيئة.

## خطوات النشر

1. ارفع محتويات النسخة الجديدة إلى نفس مستودع المشروع.
2. تأكد من إعداد `GEMINI_API_KEY` في Vercel لبيئة Production ثم أعد النشر.
3. لا تحتاج إلى Migration جديدة لهذا الإصلاح؛ لا يوجد تغيير في قاعدة البيانات.
4. بعد النشر امسح بيانات الموقع أو افتحه في نافذة خاصة لتجنب ملفات JS القديمة من cache/service worker.
5. جرّب Programming بميزانية 20,000 EGP واختَر AMD CPU. تحقق أن التجميعة AI-generated، وأن المعالج AMD، والمجموع داخل الميزانية، والتوافق بلا أخطاء.

## عند استمرار المشكلة بعد نشر هذه النسخة

إذا ظلّ fallback يظهر، فالمسبب المتبقي غالبًا ليس تحويل المحادثة داخل العميل؛ يجب فحص Logs الخاصة بـ Vercel Function `/api/ai` لمعرفة استجابة Google الفعلية: 400 (صيغة الطلب/الأدوات)، 401/403 (المفتاح أو الصلاحية)، 429 (الحصة)، 404 (معرّف الموديل)، أو 5xx (تعطل مؤقت). لا يمكن إثبات عمل مفتاح Google أو حصته من نسخة المصدر وحدها.
