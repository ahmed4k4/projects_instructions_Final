# دليل إصلاح وتشغيل Nexus في الإنتاج

هذا الدليل يشرح الإعدادات التي لا يمكن تضمينها داخل ملفات المشروع لأنها تخص حسابات Vercel وSupabase وGoogle. لا تضع أي مفتاح سري في Git أو في متغير يبدأ بـ `VITE_`.

## 1. إصلاح مسار Gemini على Vercel

كان مدخل `/api/ai/*` يجمع بين معالجات HTTP المسماة ومدخل `default` يستقبل Web `Request`. في تشغيل Node التقليدي يمكن أن يصل إلى المدخل كائن Node request بدل Web Request، فيتعطل تكوين عنوان URL ويرجع 500 قبل إرسال الطلب إلى Gemini.

تم توحيد المدخل إلى Vercel Web Standard:

```ts
export default {
  fetch(request: Request) {
    return handleRequest(request);
  },
};
```

كما أصبح المسار يتحقق من جلسة Supabase، ومن صلاحية المسار والموديل وحجم الطلب، ثم يستهلك حد الاستخدام الذري في قاعدة البيانات قبل الاتصال بـ Gemini.

### متغيرات Vercel

من Vercel افتح **Project → Settings → Environment Variables** وأضف القيم التالية للمشروع نفسه:

| المتغير | النوع | أين يُستخدم |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | عام | المتصفح وعمليات الدخول والبيانات |
| `VITE_SUPABASE_ANON_KEY` | عام | المتصفح فقط، آمن للنشر مع RLS |
| `VITE_APP_URL` | عام | رابط الموقع لإعادة توجيه تسجيل الدخول ومشاركة التجميعات |
| `SUPABASE_URL` | سري/Server | التحقق من جلسات المستخدم على الخادم |
| `SUPABASE_ANON_KEY` | سري/Server فقط | التحقق من الجلسة واستهلاك حد الذكاء الاصطناعي |
| `GEMINI_API_KEY` | سري/Server فقط | الاتصال بـ Google Gemini |

يجب أن تشير متغيرات Supabase كلها إلى **نفس المشروع**. لا تستخدم `VITE_GEMINI_API_KEY` أو `VITE_SUPABASE_ANON_KEY` مطلقًا.

فعّل متغيرات الخادم لبيئات Production وPreview، وأضف Development عند الحاجة. بعد الإضافة أو التعديل نفّذ Redeploy؛ تغيير المتغيرات لا يحدّث Deployment منشورًا بالفعل.

### تطبيق قاعدة البيانات

من مجلد المشروع:

```bash
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

تأكد أن كل migrations حتى `011_atomic_ai_usage_quota.sql و013_authenticated_ai_quota.sql` تم تطبيقها. الـ migration رقم 011 ينشئ الدالة `public.consume_ai_usage` التي تطبق حدًا ذريًا قدره 60 طلبًا لكل مستخدم خلال 60 ثانية، ولا تسمح باستدعائها إلا لـ `service_role`.

### النشر والتحقق

```bash
supabase functions deploy retailer-sync --no-verify-jwt
pnpm install --frozen-lockfile
pnpm build
```

ارفع التعديلات إلى Git المرتبط بـ Vercel أو نفّذ Deploy من لوحة Vercel. ثم تحقق من:

```bash
curl -i https://YOUR_DOMAIN/api/ai/config
```

الاستجابة الصحيحة عند اكتمال إعداد المتغيرات تكون JSON فيها `ok: true` و`gemini: true`. هذه الاستجابة تثبت وجود إعدادات الخادم، لكنها لا تختبر مفتاح Google فعليًا ولا تثبت تطبيق migration 013. الاختبار الفعلي يحتاج حسابًا مسجلًا ببريد مؤكد؛ طلبات الإنتاج دون جلسة صالحة ترجع 401، وفشل حد الاستخدام/قاعدة البيانات يظهر 503 مع سبب في سجلات Vercel.

حدود الحماية الحالية: 60 طلبًا لكل مستخدم في الدقيقة، جسم JSON بحد أقصى 2 MiB، والمكالمة إلى Google بمهلة 55 ثانية. هذه حدود تشغيلية وليست بديلًا عن حماية حساب Google ومراقبة الاستهلاك.

## 2. تشغيل تحديث أسعار المتاجر

المتصفح لا يقوم بعمل scraping. مسار البيانات هو:

1. عند وجود جدول Supabase `retailer_products` تتم قراءة بياناته بوصفه المصدر الأساسي.
2. وظيفة Supabase `retailer-sync` تجمع بيانات المتاجر المدعومة وتكتب نتائجها مع وقت آخر مزامنة في `retailer_sync_runs`.
3. إذا لم تتوفر قاعدة البيانات أو لم يكتمل أول Sync، يستخدم الموقع Snapshot منشورًا داخل `public/data/retailer_snapshot.json` كحل احتياطي. هذا الملف ليس API لحظيًا؛ وقت التقاطه موجود في `capturedAt`.
4. Sigma يحتاج متصفح Playwright منفصلًا، لذلك يحدّثه GitHub Actions عبر `.github/workflows/sigma-feed.yml`.

### إعداد مزامنة المتاجر الأساسية

تأكد من نشر `retailer-sync`، ثم فعّل امتدادي `pg_cron` و`pg_net` في Supabase Database Extensions. جدولة migration 009 تستخدم إعدادين سريين من قاعدة البيانات:

- `app.settings.supabase_url`
- `app.settings.service_role_key`

اضبطهما من إعدادات قاعدة البيانات في لوحة Supabase، أو عبر إعدادات قاعدة البيانات الإدارية. لا تحفظ service-role key في ملف SQL أو Git. بعد ضبطهما، تأكد من وجود مهمة `retailer-sync-daily` في `cron.job`. الجدولة الافتراضية هي 01:00 UTC (03:00 بتوقيت القاهرة الشتوي و04:00 في الصيف).

للتشغيل اليدوي عند الحاجة، استخدم استدعاء Edge Function مع `Authorization: Bearer SERVICE_ROLE_KEY` من بيئة آمنة، وليس من المتصفح.

### إعداد Sigma

تمت إضافة Workflow يومي في GitHub Actions. من إعدادات المستودع افتح **Settings → Actions → General → Workflow permissions** واختر صلاحية **Read and write permissions** حتى يستطيع الـ Workflow تحديث `public/data/sigma_products.json`.

شغّل `Refresh Sigma Computer catalogue` يدويًا مرة بعد تفعيل الـ Workflow للتأكد من نجاح Playwright. عند نجاح الالتقاط، ينشئ Workflow commit جديدًا؛ وإذا كان Vercel متصلًا بالفرع نفسه فسيبدأ Deploy تلقائيًا. عند رفض الموقع للـ crawler أو تغيّر تصميمه يفشل التشغيل ولا يستبدل الملف الجيد بملف فارغ.

## 3. ما تغير في تجربة الاستخدام والأداء

- صفحات التطبيق محملة بشكل كسول حسب المسار بدل تحميل كل الصفحات معًا.
- الأجهزة بعرض أقل من 768px والأجهزة ضعيفة الموارد تستخدم صورة Hero ثابتة ولا تحمّل مكتبة Three.js الكبيرة.
- تم تخفيض دقة الرسم وعدد الجسيمات في مشهد 3D المكتبي لتقليل استهلاك GPU واحتمال فقدان WebGL context.
- ملفات أسعار المتاجر تعيد المحاولة بعد الفشل بدل الاحتفاظ بنتيجة فاشلة لبقية جلسة المستخدم.
- ملف Sigma يعيد المحاولة بعد مهلة قصيرة بدل إبقاء نتيجة فارغة طوال الجلسة.
- حالة Snapshot أصبحت مميزة عن حالة المزامنة الناجحة، حتى لا يتم تقديم لقطة محفوظة باعتبارها Sync مباشرًا.

## 4. فحوصات قبل الإطلاق

نفذ محليًا بعد تثبيت الاعتمادات:

```bash
pnpm verify:spa
pnpm verify:ai-route
pnpm check:i18n
pnpm check:rtl
pnpm verify:coverage
pnpm verify:retailers
pnpm audit:mobile
pnpm test
pnpm typecheck
pnpm build
```

فحوصات `verify:retailers` تتصل بالمواقع الخارجية فعلًا وقد تفشل بسبب حظر crawler أو تغيّر موقع المتجر؛ لا يعني هذا بالضرورة أن بناء الواجهة فشل. أما `pnpm build` و`pnpm test` و`pnpm typecheck` فهي فحوصات أساسية لا ينبغي تجاوزها قبل النشر.

## 5. أمان الملفات

لا ترفع `.env.local` أو `supabase/.env.local` أو مجلد `.vercel` إلى مستودع عام. إذا سبق مشاركة ملف يحوي مفاتيح فعلية خارج نطاق خاص، ألغِ المفاتيح القديمة وأنشئ مفاتيح جديدة من لوحات Google وSupabase، ثم حدّث قيم Vercel.

## تحديث 3 نوفمبر 2026 — تسريع الذكاء الاصطناعي والجنيه المصري

### مسار Gemini

- النموذج الأساسي للمحادثة التفاعلية: `gemini-3.5-flash-lite` لتقليل زمن الاستجابة.
- عند `404` أو `429` أو `503` يجرب النظام نموذجًا بديلًا واحدًا تلقائيًا ويحفظ النموذج الذي نجح للمحادثات التالية.
- مهام البناء والتحليل متعددة الخطوات تستخدم `gemini-3.8-flash` أولًا، ثم `gemini-3.6-flash` و`gemini-3.5-flash-lite` كبدائل عند أخطاء النموذج غير المرتبطة بالحصص. خطأ 429 لا يبدّل الموديل تلقائيًا لأن الحصة تُطبّق على مستوى المشروع وقد يؤدي التبديل إلى استهلاك طلبات إضافية.
- Gemini 3.8 Flash يدعم نافذة سياق تصل إلى مليون token وفق توثيق Google؛ هذا لا يعني مليون token مجانيًا أو أن حصص المشروع غير محدودة.
- مستشار المحادثة يحتفظ بآخر 12 رسالة فقط، ويقص الرسائل الطويلة جدًا، ويحد الإجابة الافتراضية إلى 768 token لتقليل وقت التوليد.
- تنفيذ أدوات الوكيل المستقلة أصبح متوازيًا، مع تقليل الحد الأقصى لجولات الأدوات لتجنب الدوران الطويل.
- التحقق من مستخدم Supabase أصبح عبر Auth REST ثم RPC مباشرة عبر PostgREST؛ لا يعتمد ملف Vercel على `admin.auth.getUser` وبالتالي يزول تعارض `SupabaseAuthClient.getUser` في TypeScript. بصمة SHA-256 للجلسة فقط تُخزّن مؤقتًا 20 ثانية لتجنب طلب Auth متكرر داخل جولات الوكيل.
- حد التطبيق أصبح 60 طلب AI لكل مستخدم في الدقيقة. هذا حد حماية داخلي وليس زيادة لحصة Google؛ حدود Google الفعلية تعتمد على المشروع والخطة والموديل وتظهر في AI Studio.

### العملة

- كل الأسعار والميزانيات في الواجهة ومطالبات الذكاء الاصطناعي أصبحت بالجنيه المصري `EGP` فقط.
- ميزانية Smart Builder الافتراضية أصبحت 75,000 جنيه، والاختيارات السريعة أصبحت 50,000 و75,000 و100,000 و150,000 و225,000 جنيه.
- نطاق شريط الميزانية أصبح 20,000–250,000 جنيه بخطوة 5,000 جنيه.
- Build Doctor ومستشار التجميع لا يستخدمان الدولار في الأسعار أو قيمة الترقية.
- تأكد من تطبيق migration `010_price_units.sql` ثم `012_legacy_build_prices_egp.sql` على قاعدة البيانات المستضافة؛ الأولى توحّد أسعار المكونات القديمة، والثانية تصلح أسعار القطع المحفوظة وقت الإضافة وتحدّث علامة العملة. لا يكفي تغيير تنسيق العملة في الواجهة إذا كانت قاعدة البيانات نفسها ما زالت تحتوي قيمًا بالدولار.

### النشر

بعد رفع النسخة، تأكد من وجود `GEMINI_API_KEY` و`SUPABASE_URL` و`SUPABASE_ANON_KEY` في بيئة Vercel Production ثم أعد النشر. `GEMINI_MODEL` يحدد اسم الموديل المعروض في تشخيص الإعداد؛ اختيار الموديل الفعلي يتم من سلسلة النماذج داخل `src/services/ai/models.ts`.


## تحديث 014 — استخدام الذكاء الاصطناعي كزائر

- طبّق migration `014_guest_ai_quota.sql` بعد `013`.
- أضف `AI_RATE_LIMIT_SALT` كقيمة عشوائية طويلة في Vercel (Server-only، بلا بادئة `VITE_`).
- لا يحتاج الزائر إلى تسجيل دخول لاستخدام AI؛ حد الزائر 30 طلبًا/دقيقة لكل عنوان IP مجزّأ. الحساب المسجل والمؤكد يحصل على 60 طلبًا/دقيقة. هذه حدود حماية داخلية وليست زيادة لحصة Google.
- صفحة الحساب تستخدم اسم مستخدم + كلمة مرور، دون بريد حقيقي أو Magic Link. يتم تحويل اسم المستخدم داخليًا إلى عنوان غير قابل للاستلام على النطاق `.invalid` كي يستخدم Supabase Auth المعتاد بأمان.
- في Supabase Dashboard → Authentication → Providers → Email عطّل `Confirm email` قبل تفعيل التسجيل؛ لأن الحسابات لا تستخدم بريدًا حقيقيًا. لا توجد استعادة كلمة مرور بالبريد في هذا الوضع، لذا يجب على المستخدم حفظ كلمة المرور. لا تغيّر هذا الإعداد إذا كان المشروع يحتوي حسابات بريد حقيقية تريد تأكيدها؛ اختبره على بيئة منفصلة أولًا.
- تسجيل الدخول اختياري؛ الحفظ السحابي المرتبط بحساب يظل يتطلب حسابًا، بينما البناء والمستشار والبحث والمقارنة تعمل كزائر.
