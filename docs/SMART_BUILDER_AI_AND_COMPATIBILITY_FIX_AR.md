# تقرير الإصلاح النهائي — Smart Builder والتوافق

## المشكلة التي ظهرت للمستخدم

كانت صفحة Smart Builder تنتهي أحيانًا برسالة fallback بعد 8 جولات و27 استدعاء أداة ناجحًا، لكن بدون أي اختيار كامل تم التحقق منه. كما كانت قائمة «العناصر المتوافقة فقط» قد تخفي فئات مثل GPU وPSU عندما لم تكن القطع المرتبطة قد اختيرت بعد أو عندما لم تتوفر بيانات كافية للحكم.

## السبب الجذري وما تم تغييره

### 1. مسار اختيار AI جديد قبل استنفاد جولات الأدوات

- أصبح النظام يبدأ بتحميل قائمة حقيقية ومحدودة من جميع فئات القطع من الكتالوج، وليس الاعتماد على الفئات التي يتذكر النموذج البحث عنها.
- يرسل هذه القائمة إلى Gemini في طلب اختيار مستقل ونظيف، بعيدًا عن سجل محادثة الأدوات الطويل.
- يحاول أولًا إخراج JSON مقيدًا باستخدام schema.
- إذا رفضت واجهة النموذج صيغة schema أو لم تنتج JSON صالحًا، ينتقل إلى طلب AI مستقل يعيد JSON عاديًا ثم يتحقق منه الخادم.
- إذا فشل الاختيار المباشر، يكمل النظام مسار الأدوات المعتاد، ثم يجرب استدعاء `finalize_build` إجباريًا.
- رسائل التعليمات الإضافية تُدمج في دور المستخدم الحالي عند الحاجة لتجنب إنشاء أدوار متتالية غير لازمة في محادثة Gemini.
- فشل الاتصال أو تجاوز الحصة أو غياب الإعدادات لا يؤدي إلى تكرار محاولات غير مفيدة؛ بل يُعاد سبب التوقف بدقة.

### 2. قائمة AI تراعي الميزانية

كانت قائمة كل فئة تميل إلى عرض أعلى القطع أداءً فقط، ما قد يخفي الخيارات الاقتصادية التي يحتاجها النموذج لإكمال تجميعة منخفضة الميزانية.

أُضيف `selectBudgetBalancedCandidates` لتكوين قائمة متنوعة من:
- القطع الأقل سعرًا.
- القطع الأعلى أداءً.
- القطع الأفضل قيمة مقابل السعر.

ويُفضّل ترتيب حالة المخزون: متوفر، ثم كمية محدودة، ثم غير مؤكد. لا تدخل القطع التي أكد المتجر نفادها، ولا القطع التي يتجاوز سعرها الميزانية الفردية.

تم تطبيق القائمة المتوازنة على كل من `getFinalisationSnapshot` وأداة `list_components`.

### 3. التحقق النهائي من كل اختيار

لا يعرض النظام النتيجة كمبنية بالذكاء الاصطناعي إلا بعد التحقق من:
- أن كل معرّف موجود فعلًا في الكتالوج الذي شاهده النموذج.
- أن الفئة التي أرسلها النموذج تطابق الفئة الحقيقية للقطعة.
- عدم اختيار أي قطعة مؤكدة النفاد.
- وجود CPU وMotherboard وRAM وStorage وPSU وCase.
- عدم وجود فئتين مكررتين.
- عدم تجاوز مجموع الأسعار للميزانية.
- احترام تفضيل AMD Ryzen أو Intel Core.
- عدم وجود تعارضات توافق مؤكدة وفق محرك التوافق.

### 4. فلتر التوافق في صفحة بناء الجهاز

- الفلتر يخفي التعارض المؤكد فقط.
- حالات `unverified` و`review` تظل ظاهرة بعلامة محايدة؛ غياب البيانات أو عدم اختيار القطعة المقابلة لا يعني أن القطعة غير متوافقة.
- هذا يمنع اختفاء قوائم GPU وPSU قبل اختيار القطع المرتبطة بها أو اكتمال معلوماتها.
- أُبقيت قواعد التوافق الأساسية مدمجة مع قواعد Supabase حتى لا يؤدي جدول ناقص إلى اختفاء قواعد GPU/PSU.
- عند اختيار قطعة، يوقف الموقع الإضافة عند وجود تعارض مؤكد، ويعرض سببًا مفهومًا. عند تعذر التحقق، يضيف القطعة مع تنبيه واضح بدل ادعاء التوافق.

## حدود الفحص

- لا يوجد `node_modules` في بيئة الإصلاح؛ لذلك لم يتم تشغيل `pnpm typecheck` أو `pnpm build` أو Vitest الكامل.
- لم تتوفر مفاتيح Gemini وSupabase الحية في بيئة الفحص؛ لذلك لا يمكن الادعاء بأن طلب AI حي تم اختباره على مشروع الإنتاج.
- اختبارات API المحلية تحاكي Gemini وSupabase، وتتحقق من مسارات الخادم، لكنها لا تثبت صلاحية المفتاح أو الحصة أو صلاحيات المشروع الفعلي.

## النشر

هذه التعديلات كودية ولا تتطلب Migration جديدة في Supabase. ارفع المشروع كاملًا إلى GitHub ثم نفّذ Redeploy على Vercel. لا تغيّر مفاتيح البيئة بسبب هذا الإصدار.

بعد النشر جرّب Smart Builder بميزانية 20,000 جنيه مع اختيار AMD CPU. إذا عاد fallback، ستحتوي الرسالة الجديدة على سبب اختيار AI الفعلي ضمن `recovery:`، وستظهر تفاصيل إضافية في Vercel/Console تحت بادئة `[Smart Builder]`. يمكن مشاركة نص السبب بعد إخفاء أي بيانات خاصة؛ لا ترسل مفاتيح API أو Service Role.
